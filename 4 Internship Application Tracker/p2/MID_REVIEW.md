# MID-PROJECT REVIEW — Internship Application Tracker

**Project path:** `p2`
**Review date:** 2026-07-08
**Review stage:** After secondary-feature stage (filter), before testing, security hardening, and maintainability cleanup.
**Reviewer note:** Code-only review. No source files were modified, no packages were installed, no tests were created.

---

## 1. Mid-Review Summary

The prototype is structurally sound and closer to complete than a typical mid-stage build. Both the React frontend and the Express/MySQL backend are present, separated, and wired together. The main workflow (submit → list → review/approve/reject) is fully implemented. The secondary feature (filter by company name and status) is implemented. The protected action (coordinator comment and approval/rejection) is protected in the backend via a database-verified role check. A users table with seed data exists. `npm run db:setup` and the schema SQL are both present and repeatable.

The main weaknesses at this stage are:

- **No real session token or JWT.** The login endpoint returns a `mock-token-*` string that is never verified. The backend authenticates every subsequent request purely by looking up the raw `x-user-id` integer from a custom HTTP header in the database. A client that knows any valid user ID can impersonate that user with zero friction.
- **Plaintext passwords** in the database (documented as a workshop simplification).
- **The `test.js` file constitutes an early implementation** of the testing stage that was not yet requested, meaning stage drift is present.
- **No `.gitignore` in the backend directory**, so `.env` with real credentials could be committed.
- **CORS is fully open** (`cors()` with no origin restriction).
- **Frontend `studentName` is an editable field** on the submission form — a student can submit a false name because the backend reads `studentName` from the request body, not exclusively from the authenticated user record (the backend uses `username` from `req.user`, but the frontend also sends a `studentName` field that the backend ignores for the INSERT — this is correct on the backend side, but the UI field is misleading).
- **Date field mismatch:** `submittedDate` is generated automatically by the frontend (`new Date().toISOString()`) but it is not generated by the backend; the backend accepts it as a body field, meaning a client could forge a past submission date.
- **No input length limits or sanitisation** on string fields beyond required/empty checks.
- **No `DELETE /api/applications/:id`** route — a student cannot withdraw/cancel a submitted application.
- **No scroll or pagination** on the application list.
